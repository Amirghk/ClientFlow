# MVP architecture

ClientFlow is a modular monolith with five production projects. API owns controllers, JWT integration, Problem Details, typed HTTP settings, logging and telemetry. Application orchestrates organization and workspace use cases through explicit persistence/current-user interfaces. Domain owns archival, version checks, stage changes, conversion eligibility, project dates, invitations and administrator rules. Infrastructure owns EF Core, PostgreSQL mappings/migrations and repositories. Common owns shared index names. Each project has its registration extension, composed by Program.cs.

The model uses richer behavior for invariants and direct transaction-oriented application services for straightforward CRM operations. Organization is the membership aggregate and concurrency boundary; a version update prevents competing member changes from removing every administrator. Business aggregates reference other aggregates by ID. Company/contact relationships and project/task/assignee relationships use tenant-scoped database foreign keys. The opportunity/contact key also guarantees that the selected contact belongs to that company. Accordingly, a contact's company is immutable to preserve historical references.

Tracked records carry GUID concurrency tokens. Application checks submitted versions; EF checks the stored version when committing. Conversion touches the source opportunity, creates its project, and records activity in the same EF transaction. A unique tenant/source index prevents duplicate conversion. Invitation acceptance consumes the token and changes the organization together. Database concurrency/relationship races produce a reloadable 409. Each API request is a unit of work; SaveChanges provides its atomic transaction. Activity is an immutable historical snapshot, not an event bus or external side effect.

Amounts are decimals with explicit currency, timestamps are UTC, and business dates are DateOnly. Queries are explicitly organization-scoped; there is no caller-controlled tenant filter bypass. Search is bounded and sorting allowlisted. Authorization uses a verified Auth0 subject mapped to the local user; profile names never grant rights. The system assumes a single configured Auth0 issuer.

The frontend uses React/TypeScript/Vite, React Router, TanStack Query, Tailwind and local shadcn-style Button/Dialog components built on Radix primitives. The Auth0 React SDK handles Universal Login and access tokens. Shared workspace presentation is supplied either by the authenticated API session or the isolated read-only demo session. Real API failures remain failures. Query keys contain user and organization IDs; switching organizations/logout clears cached data. Failed optimistic pipeline changes restore the prior result before refetching.

Tests favor domain outcomes and database-backed HTTP behavior. JWT validation is real in HTTP tests, with a test-only signing key/discovery fixture. Default tests use SQLite; the PostgreSQL mode applies actual migrations to isolated databases. PostgreSQL-specific checks exercise competing snapshots and uniqueness. Browser tests explicitly distinguish the standalone demo from simulated API workflows. Neither proves live Auth0 connectivity, which remains a manual connection-dependent check.

Scope limits: no deployment, background email, payments, file storage, messaging, exchange rates, or external provisioning. Invitations are manually shared links. In-process rate limiting and local configuration are used by the application; a deployment must select its own hosting, secret management, HTTPS/proxy configuration, backups and observability collector.
